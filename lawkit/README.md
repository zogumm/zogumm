# lawkit — 법규검토 룰 저장소

자곡동 271-4 건폐율이 20% 로 나온 사고에서 출발했다.
대지는 **자연녹지지역 + 개발제한구역 + 취락지구**였고, 실제 건폐율은 **60%** 였다.

## 무엇이 잘못됐었나

도구는 데이터가 없어서 틀린 게 아니다. 화면에 이미 다 있었다 —
"구역 2건", "58건, 자연녹지지역·개발제한구역·취락지구".
**데이터를 가져와놓고 계산 함수가 읽지 않았다.**

```js
const 건폐율 = Math.min(법정상한, 조례)   // 20, 20 → 20
```

특별법 특례는 **완화 방향(60%)** 이라 `min()` 으로는 구조적으로 잡히지 않는다.
"가장 엄격한 값"은 준법 검사기의 규칙이지, 최대 면적을 뽑는 도구의 규칙이 아니다.

하필 자연녹지 조례 20% 와 GB 기본 20% 가 **우연히 같은 숫자**라서,
결과만 보면 맞아 보였다. 그래서 근거를 함께 출력하지 않으면 이 계열 버그는 계속 숨는다.

## 구조

```
check.js                CLI — 대지 조건으로 검토 1건
resolver.js             판정 엔진 — gate → override → cap
resolver.test.js        회귀 22건 (271-4 포함)
rules/*.json            검수된 룰. 계산은 이것만 읽는다.
laws.py                 수집 대상 법령 목록 (여기에 한 줄 추가하면 따라온다)
fetch.py                본문 + 별표 수집 / 개정 감지
test_fetch.py           파서 20건 — 네트워크 없이 돈다
data/                   수집물 (gitignore)
  manifest.json         법령별 시행일자 — 개정 감지의 기준점
```

`fetch.py` 는 파싱과 네트워크를 분리해뒀다 (`parse_search`, `parse_byeolpyo`,
`plan_attachment` 는 순수 함수). 실제 API 응답이 픽스처와 다르면 그 JSON 을
`test_fetch.py` 에 추가하고 파서를 고치면 된다 — 어디가 깨졌는지가 바로 드러난다.

## 세 개의 연산

| 연산 | 하는 일 | 누가 쓰나 |
| --- | --- | --- |
| `gate` | 트랙을 연다/닫는다 | 구역 감지 |
| `override` | 값을 갈아끼운다 | 특별법 특례 (완화) |
| `cap` | 상한을 씌운다 (`min`) | 법정상한, 조례 (강화) |

**순서가 전부다.** `gate → override → cap`. 이 순서를 지키면 새 특별법 지구는
룰 추가만으로 붙고, 어기면 지구가 바뀔 때마다 같은 사고가 반복된다.

조례는 특별법 특례를 덮지 못한다. 국토계획법 시행령 §84④1호가 집단취락지구를
GB법령에 통째로 넘겼고, 특별법에는 조례 계층 자체가 없다. 그래서 `override` 된
값에는 `cap` 을 씌우지 않는다.

### 상태값

| status | 언제 | 숫자를 내나 |
| --- | --- | --- |
| `OK` | 룰이 매칭됨 | 낸다 (근거 동봉) |
| `INPUT_REQUIRED` | 용도에 따라 값이 갈림 | **분기표를 낸다** |
| `NEEDS_REVIEW` | 특별법 구역인데 룰이 없음 | **내지 않는다** |

마지막 줄이 사고를 막는 지점이다. 매칭되는 룰이 없을 때 조용히 용도지역 기준으로
되돌아가면 틀린 숫자가 확신에 찬 얼굴로 나간다.

## 왜 별표를 받아두는가

- 별표 본문은 API가 텍스트로 주지 않는다. **HWP/PDF 링크로 온다.**
  매 검토마다 한글 파일을 파싱하는 건 느리고 잘 깨진다.
- 법규검토는 근거를 인용하는 작업이다. 검증되지 않은 자동 파싱 결과를 그대로 쓰면
  이번 같은 사고가 또 난다. 사람이 한 번 검수한 룰이 훨씬 안전하다.
- 별표 개정은 연 1~2회 수준이다. 실시간일 이유가 없다.

그래서 **API는 본문 조회용이 아니라 변경 감지용**으로 쓴다.

## 사용

```bash
# 검토 1건 — 자곡동 271-4
node lawkit/check.js --대지면적 331 --용도지역 자연녹지지역 --시도 서울특별시 \
                     --구역 개발제한구역,취락지구 --용도 근린생활시설 --자격 지정당시거주자

# --용도 를 빼면 트랙별 분기표가 나온다 (이 대지는 용도 없이 확정되지 않는다)
```

```bash
# 테스트 — 리졸버 22건 + 파서 20건
cd lawkit && node --test && python3 -m unittest test_fetch

# 저장소 루트에서 돌릴 때는 파일을 명시해야 한다
#   node --test lawkit/          ← 디렉터리를 모듈로 해석해 실패한다
node --test lawkit/*.test.js

python3 lawkit/fetch.py fetch --oc <아이디>    # 법령 본문 + 별표 전체 수집
python3 lawkit/fetch.py check --oc <아이디>    # 개정된 법령만 보고
```

```js
import { resolve } from './resolver.js';

resolve({
  대지면적: 331,
  용도지역: '자연녹지지역',
  구역: ['개발제한구역', '취락지구'],
  용도: '근린생활시설',
  자격: '지정당시거주자',
}, { rules });

// → 건폐율 60% · 건축면적 198.6㎡ · 연면적 300㎡ (연면적 캡)
//   근거: 구역 감지 개발제한구역 → 국토계획법 용도지역 기준 미적용
//         GB특조법 시행령 별표1 제5호 라목 · 제26조
```

`--oc` 는 국가법령정보센터 가입 이메일의 `@` 앞부분.

## 개정 감지 → 알림

`check` 가 개정을 잡으면, 그 법령을 쓰는 룰과 **그 룰로 만든 과거 검토**를 함께 띄운다.

```
⚠ 개발제한구역법 시행령 별표1 개정 (2026.9.1 시행)
   영향받는 저장 검토 3건 → 자곡동 271-4 외 2건
   [재검토]
```

이게 되려면 검토 결과에 **사용한 룰 id + 검수 버전**을 남겨야 한다 (provenance).
같은 기록이 "이 숫자가 어느 조문에서 나왔나"에도 그대로 쓰인다.

입법예고는 API에 뜨지 않으므로, 예고 단계는 국토부 보도자료 / 입법예고 RSS 로 따로 받는다.

- **확정 감지** — 법제처 API 폴링 (정확, 지연 없음)
- **예고 감지** — RSS (곧 바뀜을 미리)

## 룰 작성 규칙

1. `검수상태` 가 `미검수` 인 룰은 계산에 쓰되 **결과에 미검수 표시를 남긴다.**
2. 특별법 구역이 감지됐는데 매칭되는 룰이 없으면 **조용히 기본값으로 떨어지지 말 것.**
   `NEEDS_REVIEW` 로 세우는 편이 틀린 숫자를 확신에 차서 내는 것보다 낫다.
3. 모든 출력에 근거 조문을 동봉한다.

## 현재 상태

| 파이프라인 단계 | 상태 |
| --- | --- |
| 01 땅의 신원 | 외부 (토지이음) |
| 02 관할 판정 | **구현됨** — `gate()` |
| 03 용도 결정 | 일부 — GB 취락지구 5개 트랙. 근생 허용 업종 미확보 |
| 04 규모 산정 | 일부 — 미검수 |
| 05 면적 산정 | 일부 — 필로티·다락·옥탑 확정, **지하층 미확정** |
| 06 부속 규제 | 없음 — 주차·조경·일조 미착수 |
| 07 근거 기록 | 일부 — 결과에 `근거[]` 는 실리나, 룰 버전 기록 없음 |

- `rules/gb-chwirak.json` — **미검수.** 별표1 원문 대조 전.
- `resolver.js` 의 `용도지역시드` — **미검수.** 쓰면 결과에 경고가 붙는다.
- 미해결: 지하층이 연면적 캡에 산입되는지. 강남구청 질의 필요.
  포함이면 지하를 팔수록 지상이 1:1로 깎이고, 제외면 지하가 통째로 보너스다.
